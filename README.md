# טל ורון — אתר החתונה

אתר React + Vite + JavaScript בעברית ו־RTL. תאריך האירוע: **24.03.2027**, קבלת פנים 18:30, דואאה (DUEE), המאה ועשרים 6, ראשון לציון. חניה מול האולם.

## הרצה מהירה עם הדגמה

דרוש Node.js 22 ומעלה ו־npm. מתוך תיקיית הפרויקט:

```sh
npm ci
npm run dev
```

פתחו את הכתובת שהשרת מציג. `/` הוא אתר האורחים, `/i/demo` הזמנה לדוגמה ו־`/admin` דשבורד הדגמה ללא כניסה. נתוני הדגמה נשמרים ב־localStorage בדפדפן בלבד; אינם נשלחים ל־Firebase. לא מזינים מידע אישי אמיתי במצב הדגמה. מחיקת מפתח `tal-ron-demo-v1` ב־localStorage מאפסת את ההדגמה.

```sh
npm test
npm run test:e2e
npm run build
npm run preview
```

בדיקות המודל מאמתות מכסת מבוגרים, ספירת ילדים וסינון שדות לא מורשים. `npm run test:integration` מפעיל בדיקות Functions ו־Firestore מקומיות באמצעות Emulator (דורש Java 21; ראה בהמשך). אין צורך בסודות להדגמה.

## מסכים ונתונים

- הזמנה אישית למבוגר אחד כברירת מחדל. מנהל יכול להעלות מכסה ל־2 כדי לאפשר בן/בת זוג. ילדים מגיל 5 ומתחת לגיל 5 הם שתי קטגוריות נפרדות, מעבר למכסת המבוגרים. אין מכסה לילדים.
- תשובה מגיע/ה, לא מגיע/ה או אולי. במצב לא מגיע/ה נשמרים אפס משתתפים. אולי מאפשר ספירה צפויה אך אינו נכלל בסיכום המגיעים.
- הדשבורד סופר הזמנות בכל סטטוס, ומשתתפים מתוך מאשרי ההגעה בלבד. כל שורה היא הזמנה אישית, עם ילדים/בן זוג המשויכים אליה.
- חיפוש שם/טלפון, סינון סטטוס וצד, הוספה ועריכה, מכסות, פרטי אירוע ואיור. לא ניתן להקטין מכסה מתחת לתשובה קיימת.
- איור זמני ב־`public/images/couple.svg`. ניתן להחליף אותו בקובץ האיור המקורי, או להגדיר נתיב תמונה מקומי / כתובת HTTPS בפרטי האירוע. אין העלאת קבצים או Firebase Storage בגרסה זו.

## ייבוא וייצוא CSV ואקסל

אפשר לייבא קובצי CSV או XLSX. באקסל הייבוא קורא את הגיליון הראשון, והכותרות נמצאות בשורה הראשונה. הגדירו את עמודת הטלפון כטקסט כדי לשמור אפס מוביל. הייצוא הוא CSV.

ייצוא ב־UTF-8 עם BOM, שורות CRLF, ותווי נוסחאות מנוטרלים בייצוא לשם הגנה באקסל. טלפונים רצוי לייבא כטקסט באקסל כדי לשמר אפס מוביל. הייצוא כולל סטטוס, ספירות, הערה ומספר אישורי שליחה, ללא טוקנים אישיים. ייבוא **מוסיף** רשומות ואינו מעדכן קיימות. לא לייבא שוב את אותה רשימה. במקרה כשל באמצע ייבוא, מוצגת כמות השורות שהושלמו; יש לבדוק לפני חידוש.

כותרות נדרשות ודוגמה:

```csv
name,phone,side,maxAdults
אורח לדוגמה,0500000000,tal,1
משפחה לדוגמה,0520000000,ron,2
```

`side` הוא `tal` או `ron`, מכסת המבוגרים היא מספר שלם בין 1 ל־20. אפשר לייבא גם קבצים בפורמט הישן עם עמודות מכסת הילדים, ותוכנן לא ישמש.

## מעבר ל־Firebase אמיתי

1. צרו פרויקט Firebase ובחרו אזור Firestore מתאים (הפונקציות מוגדרות `europe-west1`). הפעילו Cloud Firestore, Hosting ו־Authentication עם ספק Email/Password. Cloud Functions דורש בדרך כלל תוכנית Blaze; פתיחת WhatsApp עצמה אינה דורשת API בתשלום.
2. צרו Web App ב־Firebase. העתיקו `.env.example` ל־`.env`, מלאו את פרטי ה־Web App ושנו `VITE_DEMO_MODE=false`. משתני `VITE_` נכנסים לקוד הציבורי: מותר לשמור בהם רק הגדרות Web Firebase ציבוריות, **לעולם לא** סיסמאות, מפתח service account או מפתח API שרת. מפתח Web Firebase אינו מנגנון הרשאה; האבטחה נעשית בשרת ובכללים.
3. צרו משתמש מנהל ב־Firebase Authentication. העניקו לו custom claim בשם `admin: true` דרך Firebase Admin SDK בסביבה מהימנה. הסקריפט `scripts/set-admin.mjs` מיועד לכך: אחרי `npm ci --prefix functions` ובסביבה עם Application Default Credentials והרשאת ניהול משתמשים, הפעילו `node scripts/set-admin.mjs UID`. אין להכניס קובץ credentials למאגר. לאחר הענקת הרשאה יש להתנתק ולהתחבר שוב. משתמש מחובר ללא claim אינו מנהל.
4. התקינו תלויות שרת: `npm ci --prefix functions`. התחברו ל־Firebase CLI עם החשבון שלכם (`npx firebase login`) ובחרו פרויקט בעזרת `npx firebase use --add`. אין פרויקט אמיתי מקודד בקוד.
5. **רק לאחר החלטה מפורשת לפרוס**, הפעילו `npm run deploy` (מפרסם Hosting, כללי Firestore ו־Functions לפרויקט שנבחר). הפקודה אינה מופעלת אוטומטית. בדקו היטב את פרויקט היעד בטרם הרצה. ניתן לפרוס בנפרד באמצעות `npx firebase deploy --only firestore:rules,functions,hosting` אחרי build.
6. התחברו ל־`/admin`, הוסיפו מוזמנים והעתיקו קישורים אישיים. אין נתוני הדגמה במסד האמיתי. הגדרות האירוע מתחילות מברירות המחדל ויישמרו ב־`settings/event` עם השמירה הראשונה.

אין צורך לבנות מחדש את הממשק לשינוי נתוני אורחים/אירוע. שינוי משתני Vite או מעבר בין מצבי הדגמה/אמת דורש build חדש.

## אבטחה וגבולות גישה

- Firestore דוחה כל קריאה/כתיבה ישירה, כולל ממנהל. כל הגישות הן דרך callable Cloud Functions. פעולות ניהול בודקות ID token מאומת עם claim `admin` בצד השרת.
- קישור אורח הוא הרשאת bearer: טוקן אקראי בן 256 ביט נוצר **בשרת**. אינדקס הגישה הוא SHA-256 בטבלת `invitationTokens`, ומפת הטוקנים חסומה ללקוחות. הטוקן המקורי נשמר ברשומת אורח חסומה כדי שמנהל יוכל להעתיק קישור שוב. יש להתייחס לקישורים כמידע פרטי ולא לפרסם/להעביר אותם. מי שמחזיק בקישור יכול לעדכן את אותה הזמנה.
- בקשת אורח מקבלת רק שם, מכסת מבוגרים ותשובה של אותה הזמנה. לא טלפון, צד, רשימות או היסטוריית שליחה. קריאת אירוע בלבד ציבורית.
- תשובה נשמרת בטרנזקציה, עם בדיקת מכסת המבוגרים וספירת הילדים בשרת. נזרקים כל השדות שאינם מותרים. אין אפשרות לעדכן מכסות דרך ממשק אורח או לבקש הזמנה לפי ID.
- Hosting מגדיר `Referrer-Policy: no-referrer`, והקישורים החיצוניים משתמשים ב־noreferrer. אין analytics המעתיק קישורים. גופנים נארזים מקומית דרך Fontsource, ללא בקשת Google Fonts חיצונית.
- לפני אירוע אמיתי מומלץ להגדיר תקציב/התראות ומדיניות שימור נתונים, ולשקול App Check בהתאם למדיניות האורחים. אין בגרסה זו חסימת קצב לכל IP או מסך ביטול/החלפת טוקן. ניתן לבטל הזמנה בסביבה מהימנה באמצעות מחיקת אינדקס הטוקן שלה; אל תמחקו רק את נתוני ההרשאה ותצפו שהלקוח ישחזר אותם.

## בדיקות מקומיות של Firebase

```sh
npm ci --prefix functions
npm run test:integration
```

הבדיקה מפעילה Emulator בלבד בפרויקט `demo-tal-ron`, יוצרת משתמשים מקומיים ובודקת מנהל, אורח, חוסר הרשאה, מכסות וכללי מסד. אינה פונה לפרויקט הייצור. לבדיקת UI מול אמולטורים הגדירו `VITE_DEMO_MODE=false`, פרטי Firebase של פרויקט הדגמה, ו־`VITE_USE_EMULATORS=true`; הפעילו `npm run emulators -- --project demo-tal-ron` ובחלון נפרד `npm run dev`. מנהל אמולטור דורש claim בדיוק כמו מנהל אמיתי. אין להגדיר `VITE_USE_EMULATORS=true` בבניית ייצור.

## WhatsApp

שלוש תבניות ושני סגנונות. בחרו נמענים, עברו על כל נמען בתצוגה המקדימה וערכו את הטקסט. שינוי הנמען/התבנית יוצר נוסח מחדש. כל פתיחת `api.whatsapp.com/send` פותחת טיוטה עבור נמען יחיד, ורק לחיצה אישית ב־WhatsApp שולחת אותה. יש לאשר שליחה ידנית באתר אחרי השליחה; פתיחת החלון אינה נרשמת כשליחה. אין בקשות API, תזמונים או משלוח אוטומטי. תזכורות מסננות טרם השיבו/אולי בהתאמה.

## מבנה

## תוצאות הבדיקות בסביבת הפיתוח הנוכחית

בדיקות מודל ובדיקות דפדפן רצו בהצלחה, וגם build ייצור. בדיקת האינטגרציה מול Firebase Emulator הוכנה אך לא הושלמה: הורדת האמולטור הרשמי מ־`storage.googleapis.com` נחסמה במדיניות הרשת (403). יש לאפשר את הדומיין בהגדרות הסביבה ואז להריץ `npm run test:integration`. אין בכך אימות של Firebase בייצור. לא בוצעו פריסה או הודעות אמיתיות.

בדיקות Playwright משתמשות ב־Chromium שב־`/usr/bin/chromium` כברירת מחדל; ניתן לשנות עם `CHROMIUM_PATH`. למחשב אחר יש להתקין Chromium או לבחור נתיב לדפדפן מקומי.

## הפרויקט שנבחר: talronwedding-1b4d7

פרטי Web Firebase שסופקו הוגדרו בקובץ המקומי `.env.local`, המוחרג מ־Git. הקובץ `.firebaserc` בוחר בפרויקט `talronwedding-1b4d7` כיעד CLI; בחירה זו אינה פורסת דבר.

- `npm run dev` ממשיך להפעיל הדגמה מקומית כדי שניתן יהיה להשתמש באתר לפני פריסת השרת.
- `npm run build` משתמש ב־`.env.production.local` כדי לבנות אתר המחובר ל־Firebase האמיתי. קובץ זה גם מוחרג מ־Git. במחשב חדש יש ליצור את קובצי הסביבה לפי `.env.example`.
- לבדיקה מקומית מול Firebase האמיתי, לאחר פריסת השירותים, אפשר להריץ `VITE_DEMO_MODE=false npm run dev`.
- Analytics לא הופעל; מזהה המדידה אינו נחוץ לאישורי הגעה.

טרם הפעלה אמיתית יש ליצור Firestore במצב production, להפעיל Email/Password ב־Authentication, ליצור מנהל ולהעניק custom claim, ולפרוס את כללי Firestore ופונקציות השרת. פריסת Functions דורשת תוכנית Blaze. גם אתר שנבנה עם ההגדרות אינו יכול לקרוא אירוע או לשמור תשובות לפני פריסת הפונקציות. לא בוצעו פריסה או שליחת הודעות בעת הגדרת החיבור.

## מניעת פרסום של מצב הדגמה

מצב הדגמה זמין רק בשרת הפיתוח של Vite. כל build לייצור משתמש ב־Firebase ובבדיקת הרשאת `admin`, ללא עקיפת התחברות. הבנייה נעצרת אם חסרים פרטי Firebase, אם מוגדר `VITE_DEMO_MODE=true` או אם מופעלים אמולטורים. יש להגדיר `VITE_DEMO_MODE=false` ו־`VITE_USE_EMULATORS=false` בקובץ `.env.production.local` יחד עם הגדרות Firebase. פקודת Firebase Hosting מפעילה build חדש אוטומטית לפני כל פריסה, כדי למנוע העלאת `dist` ישן ממצב הדגמה.

## עיצוב אתר האורחים

העיצוב בהשראת גן חתונה מאויר: שמנת, ירוק מרווה ופרחים בצבעי מים. רקע הגן נמצא ב־`public/images/wedding-garden.webp` (איור שנוצר לפרויקט, כ־193KB). האיור הזוגי נשאר נפרד ונקבע בשדה `image` של האירוע, עם `public/images/couple.svg` כברירת מחדל; ניתן להחליף אותו בלי לשנות את רקע הגן. קובץ `src/styles/guest.css` תחום ל־`.guest-site`, כך ששינויי האתר אינם משנים את הדשבורד. בנייד האיור מוצג מעל ההזמנה, וטופס ההגעה משתמש בשדות גדולים ובסימון בחירה בולט.

## תיקיית התמונות

כל קובצי התמונות והאיורים של האתר נמצאים ב־`public/images/`:

```text
public/
└── images/
    ├── couple.svg             # האיור הזוגי הזמני
    └── wedding-garden.webp    # רקע הגן המאויר
```

הוסיפו תמונות חדשות לתיקייה זו, עם שמות קבצים קצרים באנגלית וללא רווחים. באתר משתמשים בנתיב `/images/filename.webp` (ללא `public`). לאיור זוגי חדש, הוסיפו את הקובץ לתיקייה ועדכנו את שדה האיור בפרטי האירוע בדשבורד לנתיב שלו, למשל `/images/tal-and-ron.png`. יש לבצע build ופריסת Hosting כדי להעלות קבצים חדשים לאתר. הזמנות קיימות שהאיור שלהן נשמר כ־`/couple.svg` ממשיכות לעבוד באמצעות התאמת נתיב בלקוח והפניה ב־Hosting.
